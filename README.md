# PDF_OCR Picker — 請求書PDFの自動仕分け

PDFを読み取って「請求書かどうか」を判定し、指定フォルダへ振り分けるツールです。
Power Automate から呼び出せる CLI（exe）と、判定ルールを調整するためのデバッグGUIで構成されています。

- **対応言語** 日本語・英語（韓国語文書は英字の `Invoice` を手がかりに判定）
- **OCRエンジン** EasyOCR（CPU）
- **動作環境** Windows / Python 3.12
- **配布形態** PyInstaller の onedir（Python不要、フォルダごとコピーで移設可能）

> **請求書以外にも使えます。**
> このツールは請求書を前提に開発していますが、判定エンジンは「特定の語が文書内に在るか」だけを見ており、
> **文書の種類そのものには依存していません。** そのため `rules.yaml` のキーワードを書き換えるだけで、
> 領収書・見積書・注文書などの選別にも転用できます（日本語・英語の文書が対象）。
> デバッグGUIの判定結果は、そのことが分かるように「請求書」ではなく中立的な **Match / Review / Other** と表示します。
> 詳しくは [4. ルールの調整](#4-ルールの調整) を参照してください。

## 1. 設計の考え方

### 1.1 前提：レイアウトは多様だが、語彙は安定している

請求書のレイアウトは発行元ごとにばらばらで、事前に想定するのは現実的ではありません。
ただし**それが問題になるのは「項目の抽出」であって「種類の判別」ではありません。**

| 目的 | 必要なもの | レイアウト多様性の影響 |
|---|---|---|
| 金額や取引先を**抽出**する | 座標・表構造の理解 | 致命的 |
| 請求書か否かを**判別**する | 語が存在するかどうか | ほぼ無関係 |

本ツールは後者だけを行います。したがって**表の構造を一切見ません。**
見るのは「どの語が出現したか」と、補助的に「タイトルがページ上部にあるか」だけです。

請求書はレイアウトが違っても、以下の語彙がほぼ必ず現れます。

```
タイトル系 : 請求書 / ご請求書 / 御請求書 / 請求明細書 / INVOICE
金額系     : 請求金額 / 合計金額 / 消費税 / 小計
支払系     : 支払期限 / 支払期日 / 振込先 / 口座番号
制度系     : 登録番号 T+13桁（インボイス制度）
```

### 1.2 処理の流れ

```
PDF
 └─ 1ページ目のみ処理（文書が何であるかは1ページ目に書いてある）
     ├─ テキスト層あり  → PyMuPDF で抽出   ┐
     └─ テキスト層なし  → EasyOCR(ja+en)  ┘→ TextBlock のリスト（文字＋座標）
                                              │
                                    正規化はしご
                                    ＋ 元テキストへのインデックス対応表
                                              │
                                    キーワードマッチ（4戦略）
                                              │
                                    重み付けスコアリング（rules.yaml）
                                              │
                        ┌─────────────┼─────────────┐
                     ≥ 高閾値        中間           < 低閾値
                     請求書/         _要確認/       _その他/
```

### 1.3 OCRは最後の手段

会計ソフトやメール添付のPDFの多くは**テキスト層**を持ちます。
テキスト層は**即座かつ100%正確**なので、これにOCRをかけるのは遅くなるうえ精度も落ちます。

```
テキスト層  0.0 秒 / ページ
OCR         約 8 秒 / ページ（CPU）
```

したがって最初にテキスト層の有無を判定し、**無い場合だけ**ラスタライズしてOCRにかけます。
スキャナのヘッダやスタンプ由来の数文字をテキスト層と誤認しないよう、最低文字数（既定50文字）を設けています。

### 1.4 テキスト層とOCRで、マッチの厳しさを変える

取得元は結果に記録され、**マッチ戦略の厳しさを切り替えます。**

テキスト層の文字は既に正確なので、そこで曖昧マッチを許しても
**取りこぼしは救えず、誤検出を作るだけです。** よってテキスト層では完全一致に固定します。
（`fuzzy_on_text_layer: true` で無効化可能）

### 1.5 正規化とファジーマッチ（2つの別問題）

請求書がキーワードマッチを破る形は2種類あり、**対処が異なります。**

| 現象 | 例 | 原因 | 対処 |
|---|---|---|---|
| 文字は正しいが分断 | `請　求　書` | レイアウト上の字間調整 | **正規化**（空白除去） |
| 文字そのものが誤り | `請求澤書` | OCRの誤認識 | **ファジーマッチ** |

**正規化はしご**（GUIで個別にON/OFF可能）

| 段階 | 処理 | 潰せる問題 |
|---|---|---|
| NFKC | 全角英数→半角、`㈱`→`(株)`、半角カナ→全角 | `ＩＮＶＯＩＣＥ` |
| 空白除去 | 空白・タブ・改行を全削除 | **`請　求　書`**、OCRが1文字ずつ別ブロックにした場合 |
| 記号除去 | 罫線・括弧・区切り記号を削除 | `請\|求\|書`（既定オフ。最も破壊的なため） |
| 小文字化 | 英字を小文字に | `INVOICE` / `Invoice` |

**マッチ戦略**（ルールごとに指定）

| 戦略 | 内容 | `請求澤書` | `請氷書` | 誤爆リスク |
|---|---|---|---|---|
| `exact` | 完全一致 | ✗ | ✗ | なし |
| `subsequence` | 文字が順序どおり、かつ `window` 文字以内 | ✓ | ✗ | 低 |
| `fuzzy` | 編集距離 `max_distance` 以内 | ✓ | ✓ | 中 |
| `regex` | 正規表現 | — | — | 記述次第 |

`subsequence` の `window`（範囲制限）が要です。これが無いと
`請`・`求`・`書` がページ中に散らばっているだけで「タイトルあり」と判定されてしまいます。

`fuzzy` は**4文字以上のパターンにのみ許可**しています。
距離1を許すと `税込` が `税抜`（意味が正反対）にヒットするためで、
短いパターンに `fuzzy` を指定したルールは読み込み時に拒否されます。

### 1.6 判定は3値にする（誤爆コストの非対称性）

```
スコア ≥ 高閾値(70)  → 請求書/     へ移動
       ≥ 低閾値(40)  → _要確認/    へ移動  ← 人間が最終判断
       < 低閾値      → _その他/    へ移動
```

請求書でないものが請求書フォルダに紛れると、**後でそのフォルダを開いた人には気づけません。**
逆に取りこぼしは「_要確認 を見れば済む」だけです。コストが非対称なので、
**曖昧なものは推測せず人間へエスカレーションします。**

`納品書兼請求書` のように本当に両方の性質を持つ文書は、実在します。
こうした文書を捨てるのではなく `_要確認` に置くのがこの設計の意図です。

### 1.7 判定根拠を必ず残す

スコアだけでは何も調整できません。「38点でした」では、どの重みを動かせばよいか分かりません。
そこで**発火した全ルールと、実際にマッチした文字列**を記録します。

```
+30  title_seikyusho   '請求書' → '請求澤書'  (subsequence)
```

この記録が、デバッグGUIの表示・監査ログ・移動の取り消し根拠の**すべてを兼ねます。**

### 1.8 メールのプリントアウトを弾く

請求書を転送したメールを印刷したPDFは、**請求書が持つ語彙をすべて持っています。**
件名の `請求書`、本文の `ご請求金額` `お支払期限`、英字の `Invoice`。
しかしこれは請求書ではなく送り状であり、請求書フォルダに入れると
**照合先のない重複が生まれます。**

区別するのは請求書の語彙ではなく、**請求書には決して現れないメールヘッダ**です。

```
差出人 / 送信日時 / 件名 / 添付ファイル / お世話になっております
Subject: / Sent: / Attachments:
```

これらは**単独では弱く、揃うと強い**ように重み付けしています。
ヘッダの一部をOCRが読み落としても、スコアは `_要確認` 側へ寄るだけで、
請求書として誤って振り分けられることはありません。

## 3. 使い方

### 3.1 CLI（本番用・Power Automate から呼ぶもの）

**フォルダ単位で処理する `batch` を使ってください。**
`classify` をファイルごとにループで呼ぶと、OCRモデルの読み込み（数秒）を毎回払うことになります。

```bash
poetry run pdf-sorter batch "C:\in" --out result.jsonl --dry-run
```

まず `--dry-run` で「何をどこへ移動する予定か」だけを出力させ、
判定が信頼できることを確認してから `--dry-run` を外すことを強く推奨します。

```bash
poetry run pdf-sorter batch "C:\in" --move-to "C:\sorted" --out result.jsonl
```

`C:\sorted` の下に `請求書/` `_要確認/` `_その他/` が作られます。
アンダースコア始まりの2つはエクスプローラで先頭に並ぶため、人間が確認すべきものが目に入ります。

**1ファイルだけ処理する場合**

```bash
poetry run pdf-sorter classify "C:\in\one.pdf"
```

**フォルダの中身を調べる（移動しない）**

```bash
poetry run pdf-sorter diag "C:\in" --pretty
```

「このフォルダの何割にテキスト層があるか（＝どれだけOCRに時間がかかるか）」
「スコア分布がどこで割れているか」が分かります。**閾値を勘ではなく根拠で決めるための機能です。**

**主なオプション**

| オプション | 意味 |
|---|---|
| `--move-to <dir>` | 振り分け先のルート。指定しなければ何も移動しない |
| `--dry-run` | 移動せず、移動予定だけを報告する |
| `--out <file>` | 1ファイル1行のJSONL監査ログ |
| `--rules <file>` | ルールファイルを差し替える |
| `--force-ocr` | テキスト層があっても無視してOCRする |
| `--no-ocr` | OCRを行わない（テキスト層のみ、高速） |
| `--recursive` | サブフォルダも対象にする |
| `--dpi <n>` | OCR時のラスタライズ解像度（既定300） |
| `--config <file>` | 既定フォルダの config.yaml を差し替える |
| `-v` | 進捗を stderr に出す |

**フォルダの事前指定（config.yaml）**

毎回フォルダを引数で渡す代わりに、**exeと同じフォルダに `config.yaml` を置いて既定値を設定**できます。
引数を省略するとこの値にフォールバックするため、Power Automate 側は `pdf-sorter.exe batch` の一行で済みます。

```yaml
# config.yaml（exeの横に置く。マシン固有なのでリポジトリには含めない）
input_dir: C:\in
output_dir: C:\sorted
log: C:\logs\result.jsonl
```

```bash
pdf-sorter batch          # 上記3つを config.yaml から読む
pdf-sorter batch "C:\別のフォルダ"   # 明示した引数が config より優先される
```

デバッグGUIで選んだ参照フォルダ・コピー先も、この `config.yaml` に**自動保存**されます。
GUIで一度設定すれば、次回のGUI起動時にもCLI（PA）でも同じフォルダが既定になります
（`rules.yaml` はキーワード、`config.yaml` はフォルダ、と役割が分かれています）。

### 3.2 Power Automate との連携

**終了コード**（JSONを解析せずに分岐できます）

| コード | 意味 |
|---|---|
| 0 | 請求書 |
| 1 | 請求書ではない |
| 2 | 要確認 |
| 9 | エラー |

**標準出力**は JSON のみです。ログ類はすべて stderr に出ます。

日本語は `\uXXXX` エスケープで出力されます。日本語WindowsのコンソールはCP932で、
UTF-8バイトを通すと**復元不能な文字化けになる**ためです。エスケープはJSONとして完全に妥当で、
どのパーサでも元の文字に戻ります。人が読む用の `--out` JSONL は UTF-8 のままです。

```json
{"directory":"C:\\in","files":19,"elapsed":43.74,"dry_run":true,
 "verdicts":{"invoice":12,"needs_review":2,"other":5},
 "errors":0,"read_from":{"text_layer":14,"ocr":5}}
```

> **コンソールウィンドウを表示したくない場合**
> `--noconsole` でビルドしてはいけません。windowedビルドには標準出力自体が存在せず、
> JSON出力の経路が消えます。**PADの「アプリケーションの実行」でウィンドウスタイルを「非表示」に設定**するか、
> `--out` のJSONLファイルを読む方式にしてください。

### 3.3 デバッグGUI（ルール調整用）

開発環境から：

```bash
poetry run python -m pdf_ocr.gui
```

配布したexeから（Python不要）：

```bash
pdf-sorter-gui.exe
```

`pdf-sorter-gui.exe` はコンソールを出さない版で、**ダブルクリックで起動できます。**
コンソール版から `pdf-sorter.exe gui` と叩いても同じ画面が開きます。
どちらも同じバンドル内の同じプログラムで、実行ファイル名で動作を切り替えているだけです。

`File → Open folder...` でPDFのあるフォルダを開きます。

| 領域 | 内容 |
|---|---|
| 左 | ファイル一覧／判定結果／正規化トグル／マッチ設定／閾値スライダー |
| 中央 | ページ画像＋認識ボックス（ホイールでズーム、ドラッグでパン） |
| 下 | Hits・Text（生／正規化後）・Rules（編集可能）・Log |

**Hitsタブの行を選ぶと、その語がページ上で強調表示されます。**
`請求書` というルールが実際には `請求澤書` にマッチしていた、といったことが一目で分かります。

OCRは1文書につき1回だけ実行され、結果は保持されます。
**閾値スライダー・正規化トグル・ルールの重みは、保持した結果から再スコアするだけなので即座に反応します。**
再度OCRが走るのは、別の文書を開いたときと `Force OCR` を切り替えたときだけです。

`Classify all` はフォルダ全体を走査し、各ファイルに判定結果を色付きで表示します。
隣の **`Stop`** で途中停止できます（OCRはページ単位で中断できないため、
**実行中の1件が終わった時点で停止**します）。

Rulesタブで編集した内容は `Save as...` で保存します。
`Save`（上書き）にしていないのは、`rules.yaml` に各重みの根拠がコメントで書かれており、
表から書き戻すと消えてしまうためです。

#### 仕分けコピーとデバッグログ

「Sorted copy」を有効にして `Destination...` でコピー先を指定すると、`Classify all` の実行時に
各PDFが判定結果フォルダ（`請求書/` `_要確認/` `_その他/`）へ**コピー**されます
（元フォルダは変更しません。何度でも再実行できます）。**本番に近い仕分け結果を、
実際に近い形で一括目視**できます。

同時に、コピー先のルートへ **`log.txt`** が書き出されます。これは実行ログではなく、
**1文書ごとに「なぜその判定になったか」を残すデバッグログ**です。

- 判定・スコア・閾値
- **加点/減点の内訳**（どのルールが何にマッチしたか＝スコアのプロセス）
- **発火しなかった陽性ルール**（＝改善点の最有力ヒント）
- **OCR認識テキスト（正規化後＝ルールが実際に見た文字列）と生テキスト**

たとえば「請求書という語が無いのにMatchになった」文書なら、金額・支払・登録番号で加点され、
`did NOT fire` に `title_seikyusho` が並ぶ、という形で根拠がすべて残ります。
低解像度スキャンで語が拾えないときも、認識テキストを見れば
**「誤認識（請氷書）」なのか「そもそも読めていない」のか**が区別でき、直す場所が分かります。
`log.txt` は実行のたびにコピーと同様に作り直されます。

### 3.4 試験用PDFの生成

実際の請求書は機密情報を含むためリポジトリに含められません。代わりに生成器を用意しています。

```bash
poetry run python -m tools.sample_pdfs
```

`data/samples/` に54件が生成されます（18レイアウト × 3系統）。
**分類器を甘やかさない構成**にしてあります。

| 難易度 | サンプル | 何を試すか |
|---|---|---|
| hard | `invoice_05_no_title_word` | 「請求書」という語が一度も出てこない |
| hard | `invoice_06_rotated_title` | タイトルが90度回転 |
| hard | `invoice_09_korean` | 本文ハングル、手がかりは `INVOICE` のみ |
| hard | `invoice_10_delivery_and_invoice` | 納品書兼請求書 |
| hard | `invoice_11_logo_dominates_title` | 社名ロゴがタイトルより大きい |
| hard | `invoice_12_graphic_logo_reversed` | 白抜きロゴが支配的、タイトルは下部の小ラベルのみ |
| hard | `other_05_email_printout` | **メールのプリントアウト**（請求書の語彙を全部持つ） |
| hard | `other_06_email_english` | 同上の英語版 |
| medium | `invoice_04_title_below_fold` | レターヘッドがタイトルを上部1/4の外へ押し出す |
| medium | `invoice_02_spaced_title` | `請　求　書` ＋ 金額も全角空白で分断 |
| medium | `invoice_07_dense_table` | 18明細行に小さなタイトルが埋没 |
| medium | `invoice_08_landscape` | 横向きA4 |
| — | `other_01`〜`04` | 見積書・納品書・領収書・注文書 |

各レイアウトは3系統で生成されます。

- **テキスト版** — テキスト層を持つデジタルPDF（会計ソフト出力相当）
- **`scan_*`** — 200 DPIで画像化（傾き・ノイズ・JPEG劣化つき。複合機スキャン相当）
- **`lowres_*`** — 90〜110 DPIで画像化（Google ドキュメント等のブラウザ経由印刷相当）。
  劣化はほぼ純粋に低解像度で、小さな日本語がOCRで**置換誤認識**される領域（`請求書`→`請求善`、`請求金額`→`請求笠額`）

各サンプルは「本来どう判定されるべきか」を宣言しているので、コーパスはそのまま**採点表**になります。

```bash
poetry run python -m tools.evaluate
poetry run python -m tools.evaluate --no-ocr     # テキスト層のみ、高速
poetry run python -m tools.evaluate --hits       # 発火したルールを全表示
```

現状 **48/54**。不一致の内訳：

- `納品書兼請求書`（3系統）が `invoice` 判定 — 「支払いを求めている以上は請求書」という見方も成り立つため意図的に未調整
- 低解像度の一部（回転タイトル90 DPI・下部タイトルの白抜きロゴ）— OCRで物理的に読めないケース

**逆方向の誤り（非請求書を請求書と誤判定）はゼロ**です。取りこぼしは大半が `_要確認` に溜まり、
人間が拾えます。低解像度での置換誤認識対策として、4文字以上の金額・支払キーワードは
**fuzzyマッチ（編集距離1許容）**を使っています（[1.5節](#15-正規化とファジーマッチ2つの別問題)）。

## 4. ルールの調整

`src/pdf_ocr/rules.yaml` を編集します。exeの場合は**exeと同じフォルダに置かれた `rules.yaml` が優先**されるため、
再ビルドせずに、問題が起きているPC上でキーワードを追加できます。

```yaml
thresholds:
  high: 70          # これ以上 → 請求書
  low: 40           # これ以上 → 要確認、未満 → その他

normalize:
  nfkc: true
  strip_whitespace: true    # 請　求　書 対策
  strip_symbols: false      # 請|求|書 が出る場合のみ true
  lowercase: true

fuzzy_on_text_layer: false

rules:
  - id: title_seikyusho
    pattern: 請求書
    weight: 30
    match: subsequence      # exact / subsequence / fuzzy / regex
    window: 6               # subsequence の範囲制限

  - id: title_seikyusho_at_top
    pattern: 請求書
    weight: 20
    match: subsequence
    window: 6
    scope: top_quarter      # ページ上部1/4にある場合のみ加点

  - id: exclude_mitsumori
    pattern: 見積
    weight: -50             # 負の重み＝除外キーワード
    match: exact
```

**ルールは加算式です。** 位置による加点は「上部にあれば追加でN点」という
ボーナスとして書くため、ルール同士が互いを知る必要はありません。

正規表現は `(?i)` のようにインラインフラグで書いてください
（テキストは正規化で小文字化済みのため）。また `\b` は漢字と英字の境界では成立しないので、
先読み・後読みを使います。

不正なルールがあると**問題を全部まとめて**報告し、読み込みを拒否します。

### 請求書以外の文書に転用する

エンジンは語の有無しか見ないので、`rules.yaml` を丸ごと入れ替えるだけで別の文書の選別器になります。
たとえば**見積書**を拾いたいなら、タイトル・金額・有効期限などの語を陽性に、請求書側の語を除外に置きます。

```yaml
thresholds: { high: 70, low: 40 }

rules:
  # 陽性：見積書の語彙
  - { id: title,    pattern: 見積書,   weight: 30, match: subsequence, window: 6 }
  - { id: title_at_top, pattern: 見積書, weight: 20, match: subsequence, window: 6, scope: top_quarter }
  - { id: amount,   pattern: 見積金額, weight: 20, match: subsequence, window: 7 }
  - { id: validity, pattern: 有効期限, weight: 15, match: subsequence, window: 7 }
  - { id: delivery, pattern: 納期,     weight: 10, match: exact }
  # 陰性：請求書やメールを弾く
  - { id: exclude_invoice, pattern: 請求書, weight: -50, match: exact }
  - { id: exclude_mail,    pattern: 差出人, weight: -40, match: exact }
```

```bash
poetry run pdf-sorter batch "C:\in" --rules mitsumori.yaml --out result.jsonl --dry-run
```

デバッグGUIの判定結果は請求書に限定しない **Match / Review / Other** 表示なので、
このカスタムルールをそのままGUIで調整できます。

> **現時点での制約（1回の実行＝1種類）**
> スコアは1本しか出ないため、「請求書／見積書／契約書」の**多クラス同時仕分けはできません**。
> 1種類ずつルールを切り替えて実行する形になります。また `--move-to` の振り分け先フォルダ名
> （`請求書/` `_要確認/` `_その他/`）とCLIの終了コード・JSONの `verdict` は請求書向けの名前のままです。
> これらを目的ごとに切り替えたい場合は、別途 `rules.yaml` に目的情報を持たせる拡張が必要です。

## 5. exeのビルド

```bash
poetry run python -m tools.build_exe
```

`dist/pdf-sorter/` に、exe 2つ・OCRモデル・`rules.yaml` が揃った状態で出力されます。
**このフォルダごとコピーすれば、Pythonもネットワークも不要で動作します。**

```
dist/pdf-sorter/
├─ pdf-sorter.exe       CLI（Power Automate から呼ぶ）
├─ pdf-sorter-gui.exe   デバッグGUI（ダブルクリックで起動）
├─ rules.yaml           ← 編集すると両方に反映される
├─ models/              OCRモデル
└─ _internal/           依存関係（2つのexeで共有）
```

### onedir と onefile

| | ディスク | 起動時間 | スキャン1件（実測） |
|---|---|---|---|
| **onedir**（既定） | 958 MB | 0.5 秒 | 16.7 秒 |
| **onefile** | 353 MB＋ | 7.3 秒 | 21.3 秒 |

onedir には `pdf-sorter.exe`（CLI）と `pdf-sorter-gui.exe`（GUI）の**2つが入り、依存関係は共有**します。
GUIを別バンドルにするとPyTorchとOCRモデルが二重に入り、550MBほど無駄になるためです。
Qtの追加分は92MB（未使用のWebEngine等を除外済み。除外しないと634MB）。

onefile は自己完結ファイルを2つ作れないためCLI版のみですが、`pdf-sorter.exe gui` でGUIは開けます。

```bash
poetry run python -m tools.build_exe --onefile
```

onefileは圧縮されるため半分以下のサイズですが、**起動のたびに全体をTEMPへ展開**します。
どちらが適切かは呼び出し方だけで決まります。

- `batch` でフォルダ単位に1回呼ぶ → 7秒は1回きり。**onefileが合理的**
- `classify` をファイルごとに呼ぶ → 7秒 × ファイル数。**onedir一択**

### 注意点

- **モデルは同梱必須**です。frozen時は自動ダウンロードを禁止しているため、
  オフラインPCや社内プロキシ配下でも確実に動きます。ビルドスクリプトが `models/` をコピーします
- **torchのサブモジュールを除外してはいけません。** `torch.distributed` を除外すると
  ビルドは無警告で通り、**実行時に落ちます**（`torch.utils.data` が読んでいるため）。
  配布先で初めて発覚する最悪の失敗なので、specにも理由を記載しています
- **UPX圧縮は使いません。** PyTorchのDLLを壊すことがあり、これも実行時にしか分かりません
- `pdf-sorter.exe` をダブルクリックするとヘルプが表示されます。GUIを開きたい場合は `pdf-sorter-gui.exe` の方をダブルクリックしてください
- **Qtのサブモジュール除外は安全です。** QtWidgetsからimport経路のない独立モジュールのため、torchの場合と違って実行時に落ちることはありません

## 7. 安全設計

ファイル移動は取り返しがつかないため、以下を守っています。

- **上書きしない。** 2社が同じ `invoice.pdf` を送ってくるのは日常的です。
  衝突時は `invoice (2).pdf` のように連番を付けます
- **削除しない**
- **dry-runは後付けではない。** 実運用の閾値が固まるまでは `--dry-run` で運用するのが正しい使い方です。
  dry-runでも「連番付きの実際の移動先」を報告します
- **全件をJSONLに記録。** 移動元・移動先・判定・スコア・発火したルールと実際にマッチした文字列を残すため、
  ログを逆に辿れば移動を取り消せます。数か月後に「なぜこの判定になったか」を説明することもできます
